**一个重要的方法论澄清，这次新发现**：`not_used_but_tested` = 2,432 模块 / 2,306,970 行，也就是说
"未接入入口"的 231 万行代码里 **99.8% 其实都有测试文件在直接 import/测试它们**。"93.5% 代码未接入"不等于
"93.5% 代码没人测过"——真实问题是"写了、测了，但没人把它接到任何命令行入口上"，这对应两种完全不同的根因
（遗弃 vs 刻意影子隔离），处置方式也不同，见 §10 Phase 1 的分类步骤。

`tests/` 目录本身 3,276 个文件、**143.7 万行**，比 11-05 报告里没单独提过的这个数字本身就相当惊人——
测试代码量已经是源码量的 58%。其中 **1,447 个测试文件（44%）只测试"未接入入口"的代码**，对应
651,450 行只服务于不会在生产里跑到的代码路径的测试。这部分测试仍然会吃掉 CI 时间、拉长套件、
制造"全绿"的安全感，但对生产行为的保障价值存疑。

**`tools/analysis/codequality.py` 本身有个小 bug，这次顺手定位并在本地修复验证**（未改动仓库里的文件，
只在分析时用了本地修正版核对数字）：该脚本按 `path.relative_to(src.parent)` 算模块名，会带上多余的
`src.` 前缀，导致它跟 `importgraph.py` 产出的 `_used_modules`（不带 `src.` 前缀）永远对不上，
所以 `functions_used`/`hygiene_in_used_modules` 这两类统计此前实际上**恒为 0 / 恒为全集**，
不能反映真实的"已接入代码"卫生状况。修正前缀后重跑，真实数字是：

- 全部函数 119,729 个；**真正入口可达的只有 7,304 个（6.1%）**
- **已接入（生产会跑到）的代码里**：`broad except` 626 处（占全库 971 处的 **64.5%**）、
  `raise ... from None` 220 处（占全库 270 处的 **81.5%**）、`print()` 调用 274 处（占全库的 **100%**）
- 结论和直觉相反：**真正跑在生产路径上的代码，在"吞异常/裸打印"这几项卫生指标上比没人用的代码更脏**，
  不是更干净。这比"未接入代码质量差"更值得优先处理，因为它直接影响生产可观测性。

一个具体、可立刻动手的例子：`src/polymarket_alpha_lab/cli.py`（15,136 行，`main()` 单函数 5,425 行、
圈复杂度 584，与 11-05 完全一致，本周未被触碰）里，存在 **24 处完全相同的复制粘贴模式**：

```python
except Exception as exc:
    print(f"scan failed: {exc}", file=sys.stderr)
    return 1
```

（`cli.py:4508-4510` 等 24 处，子命令名不同，结构逐字相同）。这种写法会把完整 traceback 丢弃，
只留一行 `str(exc)`，对一个要跑市场扫描/纸面下单的 CLI 来说，失败时除了一行文本什么都留不下。
建议抽成一个 `_run_subcommand(name, fn)` 包装，统一走 `logging.exception()`，这是一个
**范围明确、风险极低、马上就能做**的 Phase-0/1 过渡项，不需要等大重构。

## 5. 工程基础设施：CI / 分支保护（本次最具体的新证据）

**CI 现状（已用 GitHub Actions API 直接核验，非转述）**：

- `Offline verification` 工作流：11-05 以来**每次 push main 都会触发**，11-05→11-05 之间无 CI 的缺口
  已经消失。最新一次运行（`42953130156`，对应本次 HEAD 026f9585 的推送）：
  **41,262 passed / 121 skipped / 0 failed，耗时 373 秒**（11-05 基准是 41,031 passed / 113 skipped）。
  这部分确实修复了。
- 但 `native-postgres.yml`（"Native project PostgreSQL"，真正起 Postgres 跑原生测试的那个工作流）
  **自 2026-09-20 起一次都没有运行过**（52 天）。核验原因，不是偶然：
  1. 触发器只有 `workflow_dispatch` 和 `pull_request: branches: [main]`，**没有 `push`，没有 `schedule`**；
  2. `pull_request` 还限定了一长串具体路径白名单（主要是 `research_*`/`project_postgres/**`），
     跟 papersim 的改动路径基本不重叠；
  3. 更根本的是：自 9 月下旬起项目已经转为"直接 push main、owner 授权跳过外部 PR 审查"的工作方式
     （`AGENTS.md`"owner has also authorized self-review, commits and merges without external Claude Code
     review"）——**没有 PR 就没有 `pull_request` 事件**，这个工作流在当前工作方式下**物理上没有任何触发路径**，
     不是"没人记得手动点"，而是配置和工作方式互相矛盾。
  4. 查了全部 8 个 workflow 文件：**没有一个带 `schedule:` 触发器**。"数据库 CI 每日运行"这条 11-05 的
     Phase-0 建议，目前连"每日"的机制都不存在，不是执行不到位，是从未配置过。
  - **建议**：给 `native-postgres.yml` 加一条 `schedule: - cron: '0 18 * * *'`（每日一次，不依赖文件路径
    白名单），或者至少加 `push: branches: [main]` 并去掉/放宽路径过滤——两者选一个，核心是解耦出"不依赖
    PR 事件"的触发方式。
- **分支保护 / rulesets 核验结果：GitHub 平台本身拦住了，不是没配置**。直接调 API：

  ```
  GET /repos/wmqfl861/polymarket-alpha-lab/branches/main/protection  → 403
  GET /repos/wmqfl861/polymarket-alpha-lab/rulesets                  → 403
  {"message":"Upgrade to GitHub Pro or make this repository public to enable this feature."}
  ```

  这是 GitHub 的既定规则：**私有仓库 + Free 账号，经典 branch protection 和新版 repository rulesets
  都不可用**，必须升级到 Pro/Team/Enterprise，或者把仓库转公开（不建议——仓库里有服务器 IP 等运维信息，
  见 §6）。个人 GitHub Pro 目前约 4 美元/月，是这里最便宜的解法。在升级之前，"main 分支保护"这条建议
  在 GitHub 层面没有任何办法直接落地，只能退而求其次：约定"仅通过脚本/hook 强制跑完整测试才允许 push"
  之类的本地软约束，或者先完成现有的 CI-必须-绿 要求。
- `pyproject.toml` 核验：`dev` 依赖目前只有 `pytest`，**没有 ruff、没有 mypy、没有 coverage/pytest-cov**。

## 7. 治理根因：为什么"未接入代码"数字纹丝不动

`AGENTS.md` 里现行的 **Project Iron Rule 6** 原文：

> Sustained parallel development is a project iron rule. Whenever useful, independent, non-conflicting
> work exists, keep useful collaboration capacity occupied... Do not impose a permanent lower
> coordinator-side concurrency ceiling or leave useful capacity idle merely for sequential convenience.

加上 "Codex Node Push Policy" 里的：

> After a completed Codex node is verified, committed, reviewed, and pushed to GitHub, continue to the
> next suitable task by default. Do not pause solely because a GitHub push completed.

**这两条规则合起来，正是"新代码持续产出、旧代码从不清理"的制度性原因**：规则要求并行产能"保持忙碌"、
完成一个任务后"默认继续下一个"，但**没有任何一条要求"新模块必须先接入入口"或"存量未接入代码的清理
优先于新功能"**。本周的数字完美印证了这一点——15 commit、11,307 行新增，全部进入"未接入"或"影子"桶，
2,434→2,435，旧的 230 多万行一行没削。

11-05 审核建议"改写铁律 6"排在 Phase 0 第一条。**核验结果：`AGENTS.md` 里这条规则的文字，过去 6 天
一个字没有变过。** 这是这次复查里唯一一条"连文本层面的改动都没发生"的 Phase-0 条目，建议列为下一步
最优先事项——不是因为并行开发本身有问题（WP-P4/WP-NBA 这周的验证纪律其实做得不错），而是因为规则
目前只有"保持忙碌"的正向激励，没有"存量优先于增量"的平衡条款。

**具体改写建议**（供本地 agent 参考，不是唯一写法）：在 Iron Rule 6 后面加一条平衡条款，大意是——
"当 `tools/analysis/importgraph.py` 报告的未接入模块行数超过已接入模块行数的某个比例（例如 5 倍）时，
新开并行任务里至少应有相应比例分配给'接入或删除存量未接入代码'，而不是全部投向新功能/新模型"，
并把这条检查做成 Phase-0/1 验收脚本的一部分，而不是停留在文字约定。

## 8. 架构边界缺口：`~/paper-sim/` 不在版本控制内（本次新发现）

交叉阅读 `DELIVERY_PLAN.md` §70–75 和 `docs/reviews/model-review-2026-11-07.md` 发现，大量实际驱动
纸面交易决策的脚本——`~/paper-sim/tools/backtest_euro.py`、`shadow_experiment.py`、
`understat_refresh.py`、各轮 `round39/`、`review/` 下的验证产物——**全部跑在服务器本地目录下，
从未出现在本 git 仓库的任何一次提交里**。

这带来三个具体问题：

1. 本仓库任何"入口可达性"分析（包括本报告 §3 的全部数字）天然只能看到**被 import 的库代码**，
   看不到真正触发扫描/下单决策的调度脚本本身——"未接入入口"的判断只能证明"没有被库内 CLI 调用"，
   不能证明"服务器没有在跑它"，反之亦然。
2. §72 原文自己写得很清楚："接线义务：`check_cross_league_mw` 与 `CROSS_LEAGUE_ML_CLASS` 为库内
   opt-in 强制点，服务器扫描管线（~/paper-sim 侧）在下次扫描前必须接入两者，否则跨联赛 MW 的三条件
   仍只是描述性契约。"——**库里修好了 ≠ 生产在用修好的版本**，这个缺口是项目自己承认的，不是本次审核
   臆测。
3. §72 还提到"四处同步（本地→wmqfl861、服务器→Lordakee）"，即至少存在两个远端/主机需要人工保持一致，
   没有发现任何 checksum/commit-SHA 签到机制能证明服务器当前运行的代码确实等于某个已审查的 git commit。

**建议**：优先级不低于 Phase 1 的代码精简——把 `~/paper-sim/` 下真正驱动决策的调度脚本本身纳入这个仓库
（哪怕只是只读镜像 + 一个"服务器当前运行的 commit SHA"状态文件），否则本仓库所有关于"代码质量/可达性/
测试覆盖"的结论，都只覆盖了"库"，没有覆盖"真正在跑的东西"。这也是为什么 Phase 2 的"G2 首次真实运行"
前应该加一道新的前置条件，见下节。
