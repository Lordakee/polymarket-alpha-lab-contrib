# 02 优化蓝图（蓝图 v2，2026-11-12）

这份蓝图回答三个问题：项目往哪走、改完以后长什么样、哪些事要你拍板。
它不替换你已有的两份长期文件——"自动化 0–5 级"
（`docs/superpowers/specs/2026-06-13-automated-investment-roadmap.md`）和"验证闸门 0–8"
（`docs/research/validation-gates.md`）——而是把现在的工作重新挂回这两条阶梯上。
发现的编号（G-1、P-2 等）见 [01-audit-report.md](01-audit-report.md)，需求编号（N1–N11）见该报告
第 3 节。

## 1. 一句话

**把项目收拢成一条主线、一张状态表、一条证据链**：主线是把模拟盘里的策略一步步推到小额真实盘；
状态表只有一页；证据链保证每一个纸面决定都能在事后被重算、被扣费、被拿去和市场比。

## 2. 五条设计原则

| # | 原则 | 对应你的要求 | 现在差在哪 |
| --- | --- | --- | --- |
| 1 | **仓库里的代码就是跑着的代码。** 服务器只运行仓库某个固定提交，不再有只存在于服务器上的决策脚本 | N1、N7 | P-1、G-5 |
| 2 | **每个决定都能事后重算。** 候选（包括被拒绝的）连同模型版本、数据快照、订单簿、闸门结果、代码提交号一起入库 | N1、N3 | P-4、P-6 |
| 3 | **数字只有一种口径：扣费后。** 入场判断、账本盈亏、业绩报告用同一张费率表 | N1 | P-2、P-3、P-7 |
| 4 | **先收拢，再扩张。** 不新建诊断层或界面；优先复用 V1 已经做好的数据库工具、有界读取、评分模块 | N8 | S-2 |
| 5 | **并行照旧，但"做完"要有定义。** 一个节点算完成，要么接到了入口上，要么登记为影子并写明晋级条件和到期日 | N5、N6 | G-6、S-1 |

## 3. 从现状到目标

**现状**

```
服务器 ~/paper-sim（不受版本控制）              仓库
+-------------------------------------+      +--------------------------------------+
| 逐轮脚本：取数 -> 组候选 -> 过闸门    | ---> | papersim 库：模型数学 + 闸门规则       |
|   -> 定仓位 -> 写账本 -> 结算        | 调用 |   （没有数据库代码，没有总入口）        |
| paper_sim 数据库（表结构人工维护）    |      | V1 研究管线（等启动决定）              |
| 快照、回测、评审产物（约 40 处被引用）|      | 第一代命令行 + 7 月生成的 2,223 个模块  |
+-------------------------------------+      +--------------------------------------+
```

**目标**

```
仓库（唯一正本）。服务器每次运行前记录"我跑的是哪个提交"。
+----------------------------------------------------------------------------------+
| papersim（主线）                                                                  |
|   数据适配（Polymarket 官方公共接口、xG、行情） -> 快照登记（内容校验值入库）       |
|   -> 模型 -> 总入口 decide_entry（全部闸门 + 仓位规则，一处强制）                  |
|   -> 账本 v2（全部候选，接受与拒绝都记） -> 标记价与收盘价                         |
|   -> 结算（逐笔，扣费） -> 评估（净回报、收盘价偏离、对市场基准、校准）            |
+----------------------------------------------------------------------------------+
| 平台：project_postgres、地址校验、有界读取、CI（含真实数据库通道）                 |
+----------------------------------------------------------------------------------+
| V1 研究管线：冻结待决（OD-A）       | 第一代与 7 月模块：归档（OD-B）              |
+----------------------------------------------------------------------------------+
```

变化集中在三处：决策闭环搬进仓库；账本从"三张松散的表"变成"可审计的证据库"；盈亏从毛口径变成
净口径。模型数学、冻结阈值、验证纪律都不动。

## 5. 阶梯：现在在哪一级，过下一道门要什么

你原有的阶梯是：0 级只读情报 → 1 级自动研究与纸面交易 → 2 级人工批准的交易提案 → 3 级限额真实盘
试点 → 4、5 级扩大自动化。**主线 S 现在处于 1 级的前半段**：能产生纸面交易，但证据还不满足
1 级的出门条件。

### 5.1 闸门 0–5 落到主线上

| 闸门（原文件定义） | 主线现状 | 蓝图 v2 要求 | 里程碑 |
| --- | --- | --- | --- |
| 0 数据完整：原始数据先存档，评分输入可从存档重现 | 快照是服务器上的文件，账本不记它们的校验值 | 每份输入快照登记内容校验值；每个候选记录它用的快照、订单簿和取数时间 | M1 |
| 1 信号定义：能解释每个候选为什么被接受或拒绝 | 只记录被接受的；拒绝原因不入库 | 全部候选入库，带逐项闸门结果和拒绝原因 | M1 |
| 2 样本：200 个候选观察、50 笔模拟、30 笔结算、4 周前向 | 按文档已有 58 笔结算；仅 10-30 快照的 40 笔里就混了 13 种市场类型；候选总数未知 | 按"队列"分别计数；阈值沿用原文件，不降 | M2、M4 |
| 3 成本真实：买卖价、订单簿行走、手续费、离场按可成交价、部分成交、拒单日志 | 入场有行走和费用；账本盈亏不扣费；下注额可超过行走金额 | 账本净口径；总入口断言下注额不超过行走金额；离场按买价并扣费 | M0、M1 |
| 4 预测与边际质量：Brier、分桶校准、从信号到成交的边际衰减 | 只有按市场类型的胜率和总盈亏 | 评估模块：净回报、收盘价偏离、模型对市场的对数损失、分桶校准，全部带区间 | M1、M2 |
| 5 风险与回撤：单一市场或主题不主导收益 | 10-30 快照里一个市场占了 51% 的盈亏 | 评估报告列出集中度和最大回撤；纳入晋级标准 | M1 |

闸门 6–8（提案、真实盘试点、试点晋级）在本阶段只做设计，不做实现（见第 10 节）。

### 5.2 队列

"队列"指用同一个模型、同一类市场、同一版闸门产生的一组押注。业绩只在队列内统计，不同队列
不合并成一个回报率。建议的初始队列：

- 足球·大小球·国内联赛
- 足球·两队进球
- 足球·球队总进球
- 足球·胜负盘·国内
- 足球·胜负盘·跨联赛
- 加密·触价
- 加密·到期价
- 篮球·胜负盘（影子，不入场）
- 判断型（宏观、政治等不由模型定价的押注）：单独一列，只记录，不参与任何晋级判断

### 5.3 晋级标准（建议稿，需要你批准后冻结，见 OD-G）

一个队列从 1 级（纸面）晋级到 2 级（人工批准提案），以下各条须同时满足。数字是建议值；关键是
**在数据出来之前定死，之后不改**。

| 条 | 标准 | 说明 |
| --- | --- | --- |
| A 样本 | 至少 200 个入库候选（接受加拒绝）、50 笔入场、30 笔结算，且在同一版闸门下连续前向运行至少 4 周 | 即原闸门 2 的数字，不变 |
| B 成本 | 全部盈亏为扣费后；入场价来自按实际下注额行走订单簿；提前离场按买价并扣卖出费 | 原闸门 3 |
| C 领先指标 | 收盘价偏离（买入之后到开赛前市场价朝你有利方向移动的幅度）的均值大于 0，且 95% 区间下界大于 0 | 小样本下最可靠的指标；需要多少笔取决于实际的偏离幅度，见表后说明 |
| D 对市场基准 | 在该队列扫描过的**全部**市场上（不只是下注的），逐个市场比较模型和市场隐含概率的对数损失；差值（模型减市场）的 95% 区间上界不超过 +0.010 | 防止"十个变体一起偏"。这是"不比市场差"的底线，不是"比市场好"的证明 |
| E 结果 | 扣费后回报率点估计大于 0；盈利最多的一个市场占该队列总盈亏的比例低于 30%；最大回撤不超过 10 个标准下注单位（按 250 美元一单位即 2,500 美元） | 不要求回报率区间下界大于 0——那需要上千笔 |
| F 运行 | 连续 30 天由仓库内的定时扫描无人值守运行；期间没有手工改库；账本恒等式每天通过；任取一笔可重算出相同的闸门结果 | 原则 1、2 |

暂停规则：某队列入场满 40 笔后，如果收盘价偏离均值的 95% 区间上界小于 0，或回撤超过上限，
该队列自动停止新入场，转为只记录。

为什么 C 比 E 重要：在接近五五开的市场上，单笔收益率的标准差约为 1。要以 80% 的把握检出 5% 的
真实净优势需要约 3,100 笔，10% 需要约 780 笔。收盘价偏离的波动小得多：如果平均偏离约 2 美分、
标准差约 7 美分（这两个数是假设，要等有了数据才知道），同样的把握大约需要一百笔。所以用 C 和 D
来判断"模型是不是真比市场准"，用 E 只做"没有明显亏钱"的底线检查。

## 6. 目标数据模型（账本 v2）

原则：只增不改；逐笔结算；全部候选入库；所有表放在独立的 `papersim` 模式下，不再占用
`public.decisions` 这类通用名字；现有三张表保留为只读历史，用一次性导入脚本映射到新表。

| 表 | 一行是什么 | 关键列 |
| --- | --- | --- |
| `scan_runs` | 一次扫描 | 开始时间、代码提交号、库版本、闸门版本、操作者 |
| `snapshots` | 一份输入数据（xG 快照、K 线、κ 表等） | 内容的 SHA-256（主键）、种类、来源、取数时间、字节数、存放位置 |
| `candidates` | 一个被评估的候选，无论接受还是拒绝 | 所属扫描、市场与代币标识、队列、方向、模型名与版本、中位数与各变体报价、所用快照、订单簿原文与取数时间、完整闸门报告、结论、拒绝原因 |
| `entries` | 一笔纸面入场 | 对应候选（唯一）、下注额、成交价、份数、费率、入场费、仓位档位 |
| `marks` | 某一时刻的市场价 | 入场编号、时间、买价、卖价、来源；其中一行标记为"收盘价" |
| `settlements` | 一笔入场的结局 | 入场编号（主键）、结果、离场价、毛盈亏、费用、净盈亏、证据、确认人 |
| `bankroll_events` | 一次现金变动 | 时间、金额、原因、关联入场；现金恒等式可由此逐行重算 |

`entries` 和 `settlements` 只允许插入。逐笔结算从结构上消除了 P-3 那一类重复计账。

输入快照文件本身放哪里，取决于 OD-E：推荐做法是文件留在服务器的固定目录，但**校验值必须入库**，
这样既不把几十兆的 JSON 塞进数据库，也满足"可重算"。

## 8. 治理

### 8.1 一张状态表

`DELIVERY_PLAN.md` 顶部加一页"状态板"，只回答四个问题：有哪几条线、各自在哪个里程碑、下一步
是什么、在等谁。现有的 3,550 行原样保留在后面作为历史。

记录方式默认不变：`AGENTS.md` 规定 `DELIVERY_PLAN.md` 是唯一的交付状态文件，每个节点的状态和
证据都记在它里面。所以今后的记录仍然追加为 `DELIVERY_PLAN.md` 的新小节，由协调者一个人写，
各泳道把自己的证据文字交给协调者——这样既守规则，又不会多人抢同一个文件。

本交接包里的 FX 和 M 编号是包内编号。落到 `DELIVERY_PLAN.md` 时，由协调者按现有惯例登记成
新的工作包小节（延续 WP-P 序列），并在小节里注明对应的 FX 编号。

如果你同意（OD-E），可以更进一步：把记录按线拆成 `docs/plan/track-s-log.md`（主线）、
`track-r-log.md`（备线）、`track-l-log.md`（瘦身），`DELIVERY_PLAN.md` 只保留状态板和指向它们的
链接。这需要改规则，所以不是默认做法。下文说的"计划记录"，指的就是这两种位置中现行的那一种。

### 8.2 "做完"的定义（建议写进铁律 6 的补充条款，需 OD-E）

> 一个开发节点只有同时满足以下两条才算完成：
> （a）它新增或修改的每个模块，要么能从某个入口（命令行、`scripts/`、`tools/`、定时任务）走到，
> 要么在状态板登记为"影子"，并写明晋级条件和到期日；到期未晋级的影子模块在下一个节点内移除。
> （b）节点合并后，`evidence/audit_static.py` 报告的不可达模块数不高于合并前（影子登记的除外）。

这条不限制并行的规模，只规定产出要落地。11 月的 `recalib.py` 和 `nba_model.py` 已经是这么做的。

### 8.3 并行泳道与文件所有权

每个里程碑都按"互不重叠的文件集合"切成泳道，一条泳道同一时间只有一个写入者，每个节点配一个
独立只读复审（铁律 4 不变）。固定的单写者文件：

| 文件 | 单写者 |
| --- | --- |
| `database/migrations.lock.json`、`supabase/migrations/`、两处迁移计数（`tests/test_project_postgres.py:82`、`tests/test_research_dispatch.py:351`）、`tests/test_database_persistence_iron_rule.py` 的数据库连接白名单 | 数据库泳道 |
| `DELIVERY_PLAN.md`、`AGENTS.md`、`README.md` | 协调者（M0 的文档泳道由协调者自己承担） |
| `.github/workflows/`、`pyproject.toml`、`uv.lock` | 工程泳道 |
| `src/polymarket_alpha_lab/__init__.py`、`papersim/__init__.py` | 协调者（各泳道提交导出清单，由协调者合并） |

### 8.4 正本仓库与运行版本签到

- 由你指定一个正本仓库（OD-C）。另一个要么设成只读镜像，要么停用。
- 服务器每次扫描开始时，把 `git rev-parse HEAD` 和工作区是否干净写进 `scan_runs`。工作区不干净
  就拒绝运行。

### 8.5 CI

- 真实数据库通道改为：涉及迁移、数据库适配或 papersim 存储的推送触发一次，另加每周定时一次。
  不建议每天跑：私有仓库的 Actions 分钟数有限额。
- 把 papersim 的数据库测试（账本集成、业绩视图）接进这条通道。
- 离线验证里加一条：出现 `SyntaxWarning` 即失败。

### 8.6 文档、守卫测试与改动的耦合

`README.md`、`AGENTS.md` 和工作流文件都被测试读取（G-4）；`DELIVERY_PLAN.md` 没有。任何结构性
修改都要先找出读它的测试，同一个节点里一起改，不允许为了让改动通过而删除测试。

另有三个守卫测试会拦住看起来无害的改动，动手前要知道：

- `tests/test_phase1_live_surface_guard.py`：限制 `cli.py` 等几个模块里出现与令牌、凭据、下单
